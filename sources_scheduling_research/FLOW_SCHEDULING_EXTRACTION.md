### 1. Cellular Network Traffic Scheduling With Deep Reinforcement Learning

- **Authors / Year / Venue / DOI / peer-reviewed or preprint:** Sandeep Chinchali, Pan Hu, Tianshu Chu, Manu Sharma, Manu Bansal, Rakesh Misra, Marco Pavone, Sachin Katti. **2018** (published 2018-04-25). *Proceedings of the AAAI Conference on Artificial Intelligence*, **Vol. 32, No. 1, pp. 766–774** (Thirty-Second AAAI Conference on Artificial Intelligence). **DOI: 10.1609/aaai.v32i1.11339**. **Peer-reviewed conference paper.** Affiliations: Stanford University CS/EE/Aero-Astro; Uhana, Inc. Network data provided by Telstra Corporation Ltd.
- **A. Exact problem solved:** Scheduling **High Volume Flexible Time (HVFT)** IoT traffic (software updates, data backup, pre-fetched video) in a cellular cell so that the operator serves as much delay-tolerant traffic as possible during transient congestion dips, without degrading conventional delay-sensitive traffic (voice, video, web) below a throughput floor. Verbatim framing: *"the control variable is the time when HVFT data is transferred and its share of network capacity and the reward function trades off the total HVFT traffic volume delivered with throughput degradation to other delay sensitive traffic."*
- **B. Network architecture:** Legacy/operational 4G mobile network — **single cell**, control interval **Δt = 1 minute**, planning horizon **T = one day**. **No SA/NSA, no disaggregated RAN, no slicing, no cloud-native core.** The RL agent is sited **at the cell tower** with a centralized view of the cell.
- **C. Network layer/domain:** **RAN / cell level** — cell-level congestion and throughput control. Cross-layer in the sense that it uses TCP/HTTP-level observability to classify flows (see D), but the control action is cell capacity share.
- **D. Network entities involved:** Cell tower (hosts the **RL agent/scheduler**); cell (the resource being shared); conventional UEs and **M IoT devices** (M = constant action multiplier); a **Random Forest (RF) throughput regressor**; an **LSTM congestion forecaster**; the operator. Flow classification proposed via *"monitoring HTTP request headers for source IP addresses and checking TCP packets to see if they are from IoT sensors or conventional devices."* **No gNB/CU/DU/RIC/UPF/SMF entities appear — this is a pre-5G SA paper.**
- **E. Input/state parameters (exact observation vector):** State `St = [Ct, Nt, Et]` where (verbatim) **C = congestion metric** ("effective number of users in the cell"), **N = number of sessions/connections**, **E = average cell efficiency** ("takes into account … total cell bandwidth, type of cellular technology deployed, distance of users from the cell tower, and possible obstructions"). Augmented to `st = [St, φ(S0,…,St, t, T)]` where the temporal feature extractor is `φt = [St−m, …, St, Ŝt+1, …, Ŝt+k, t, H]` — i.e. **m past states, k LSTM-forecast future states, current time index t, and a normalized "horizon left" signal H = (T−t)/T**. Raw performance logs contain **over 200 variables**; the three above are the key features.
- **F. Decision variables (exact action space):** `at ∈ [0, 1]` — **a continuous scalar: the fraction of the time slot Δt in which HVFT (IoT) data is scheduled** on top of conventional traffic. `at = 0` means yield entirely to conventional traffic. Each active control schedules traffic to **M IoT devices**, where M is a **constant action multiplier** (the authors state that dynamically optimizing M is *"a second level of optimization"* left out). Volume of IoT data transacted in t is `at · Bt · M · Δt`.
- **G. Objective function (exact reward, quoted):** `R(st, at) = α·Vt^IoT − β·Vt^loss − κ·Vt^below limit` (Eq. 3), where
  - `Vt^IoT = B̂t' · M · at · Δt` (IoT volume served),
  - `Vt^loss = B̂t · ãt · Δt − B̂t' · ãt · Δt` (bytes lost by a representative user sending at rate ãt, comparing throughput **without** vs **with** IoT),
  - `Vt^below limit = (L − B̂t')^+ · at · Δt` (bytes served below the system-wide desired minimum throughput L).
  `α, β, κ` are operator-tunable trade-off weights. **L is set approximately to the median of B in training data.** Evaluated policies: **α = 2, β = 1, κ = 1 (IoT-favouring)** and **α = 1, β = 1, κ = 1 (conservative)**.
- **H. Constraints:** Soft, reward-encoded only. (i) Conventional-traffic throughput should not fall below the limit **L** (penalised by κ·Vt^below limit); (ii) IoT traffic volume should be maximised; (iii) the authors explicitly state *"It is infeasible to always strictly keep throughput above L since even natural variation breaks this threshold."* **No formal constraint set, no per-flow delay bound, no SLA formulation.**
- **I. Scheduling algorithm + optimization method:** **Deep Deterministic Policy Gradient (DDPG)** (Lillicrap et al. 2015) with **experience replay**; variant implemented with **Google TensorFlow** and a custom **OpenAI Gym** environment. Networks: **two hidden layers of 400 and 300 units**; actor LR **0.0001**, critic LR **0.001**; L2 regularization weights **0 and 0.001**; **discount factor γ = 0.99**; **minibatch 32**. The RF throughput model (input to the reward, unknown to the agent) achieved **11.4% median error and 890 Kbps RMSE** on Melbourne data. An **offline Dynamic Programming (DP) oracle** over a discretised MDP (|S̄| = 240 states, |Ā| = 40 actions) provides the performance upper bound; stochastic **Model Predictive Control (MPC)** using the same LSTM forecast is the strongest baseline.
- **J. ML/DRL used?** **YES — Deep RL: DDPG** (actor-critic, continuous action). Plus **LSTM** for congestion forecasting (stacked two-layer, 50 units per layer; lookback m = 9, horizon k = 7; **14.8% median percentage error, RMSE 0.951 for congestion C**) and **Random Forest regression** for the throughput model.
- **K. Simulator / testbed / dataset:** **Custom data-driven network simulator built on OpenAI Gym**, released publicly (the paper cites `bitbucket.org/sandeep_chinchali/aaai18_deeprlcell`). The authors state: *"After an extensive literature search, we concluded comparable network simulators do not already exist… Existing simulators are unsuitable since they focus on wireless channel models at extremely fast timescales and not city-level congestion patterns."* **Dataset = 4 weeks of real network data from 10 diverse cells in downtown Melbourne, Australia**, collected with Telstra; metrics aggregated over Δt = 1 minute; **27 cell-day pairs (19 train, 8 test days)**. **Also: live-network experiments** — *"we introduced short file downloads to operational networks"* to validate the dynamics model (Figure 2). **This is a real-operator dataset plus limited live-network probing, with training/evaluation in a simulator — not a full testbed.**
- **L. Traffic model:** **Real network traces** (4 weeks, 10 cells, downtown Melbourne), not synthetic. Traffic classes: conventional delay-sensitive (voice, video streaming, web browsing) and IoT/HVFT (software updates, data backup, cloud sync, pre-fetched video). Congestion dynamics modelled piecewise with zero-mean Gaussian noise: `Ct+1 = Ct + M·at + ΔC̃t + εt` if `at > 0`, else `Ct+1 = C̃t + ΔC̃t + εt` (Eq. 2).
- **M. Network scale:** **1 cell per episode**; control interval 1 minute; horizon 1 day; **10 cells** in the dataset; **27 cell-day pairs** (19 train / 8 test); **M IoT devices per action** (M not numerically specified in text); **10 MHz of radio spectrum** per cell. Test days are 8.
- **N. Baselines:** (i) **Heuristic control** — *"uses LSTM congestion forecasts and the throughput model to predict future throughputs B̂k and choose an action proportional to the 'headroom' (B̂k − L)+ or an action of zero if natural throughput variation is already predicted to be below the desired minimum limit of L"*; (ii) **Stochastic Model Predictive Control (MPC)** — same LSTM forecast (k = 7), receding horizon, DP over discretised Q-tables; (iii) **Offline DP "oracle"** with perfect full-day congestion forecasts (upper bound, not a deployable baseline). *"After a thorough literature search, we concluded that there are no existing benchmarks for comparable problems and data."*
- **O. Metrics:** **IoT traffic volume gain V_IoT / V_0 (%)** where V_0 = normal traffic carried during a day; **throughput B**; **congestion C**; **percentage of upper-bound reward attained**; **statistical significance via Wilcoxon paired signed-rank test**; **operator cost saving derived from spectrum value**.
- **P. Main quantitative results (EXACT, quoted):**
  - *"The median gain across all days for the α = 2 policy was **14.7 %**, which is extremely significant for operators."*
  - *"a utilization gain of 14.7% means the operator is saved about **$661 million** that it would have otherwise spent on acquiring new spectrum"* (based on 10 MHz ≈ $4.5B spectrum cost cited from Reardon 2015).
  - *"Figure 4(a) illustrates HVFT-RL schedules **2.06×** as much IoT traffic than the heuristic, only backing off with at = 0 during peak lunch congestion hours."*
  - *"stochastic MPC (green) uses the same LSTM model as the RL agent… and performs fairly well at about **62% of the optimal solution**"*; the RL agent reaches *"just below **80% of the upper bound** for feature set C1ΔC7."*
  - Statistical: *"the distribution of α = 1 and α = 2 gains per cell-day pair are indeed different at the .05 significance level (p < .002) (Wilcoxon 1945)."*
  - Convergence: *"we observe stable convergence within **200 episodes** in all cases."*
  - Outlier context: *"the largest outlier in Figure 3 represents a Melbourne railway cell Saturday, which faces **66% less congestion** compared to 8 weekdays in our data."*
  - Discretisation tolerance: for |S̄| = 240, going from |Ā| = 40 to 60 *"only changes the reward by **0.226%**, showing the reward does not change beyond our predefined tolerance of 0.5%."*
- **Q. Main limitation:** **Author-stated:** (i) the agent is evaluated in a **simulator** built from the operator's data — *"Future work centers around deploying an RL agent in an operational network to validate gains"*; (ii) **action multiplier M is fixed**, not learned; (iii) the policy is **restricted to stationary policies for tractability**; (iv) the test/train gain gap is attributed to finite data (*"As we collect more data, this gap should decrease"*). **Methodological:** (a) **single cell, single day horizon, one traffic dimension** — no multi-cell coordination, no inter-cell interference, no core network, no slicing; (b) the reward depends on a **learned RF throughput model** whose own error (11.4% median) propagates into the training signal; (c) the **oracle is a discretised DP approximation**, so "80% of upper bound" is relative to an approximation of the true bound; (d) **energy, delay percentiles, and fairness to conventional users are not metrics**; (e) no public dataset (operator-proprietary) — only the simulator code is released.
- **R. Research gap this suggests:** (i) **The action space is one scalar per cell** — the natural extension to per-flow / per-QoS-flow / per-slice scheduling across many cells is completely open and is exactly what the 5G papers below attempt in far narrower settings; (ii) the RF-in-the-loop reward is a **model-based reward with unquantified bias** — a model-free or uncertainty-aware reward would be a genuine contribution; (iii) **no delay-percentile or SLA constraint** is enforced, only a soft throughput floor — modern 5QI/URLLC work needs hard bounds; (iv) **safety during exploration in a live network is named as a challenge but not solved** — safe/constrained RL for production cellular schedulers remains open; (v) **flow classification (IoT vs conventional) is proposed but assumed perfect** — misclassification robustness is untested; (vi) the study predates 5G SA, disaggregated RAN, and O-RAN, so **no AI-native control-plane integration** (RIC/xApp) exists here — this is precisely the architectural gap that papers 8 and 9 fill.
- **S. Best URL actually retrieved + read level:** `https://ojs.aaai.org/index.php/AAAI/article/view/11339/11198` (AAAI open proceedings, CC-licensed). **FULL TEXT READ** (9 pages, all sections including Eq. 1–3, Figures 1–5, full evaluation).

### 2. Intelligent Resource Scheduling for 5G Radio Access Network Slicing

- **Authors / Year / Venue / DOI / peer-reviewed or preprint:** Mu Yan, Gang Feng, JianHong Zhou, Yao Sun, Ying-Chang Liang. **2019** (issue August 2019). *IEEE Transactions on Vehicular Technology*, **Vol. 68, No. 8, pp. 7691–7703**. **DOI: 10.1109/TVT.2019.2922668**. **Peer-reviewed journal.** Affiliations: National Key Laboratory of Science and Technology on Communications & Center for Intelligent Networking and Communications (CINC), University of Electronic Science and Technology of China (UESTC), Chengdu; Xihua University. Funding: NSFC 61631005; Guangdong R&D Program 2018B010114001. **Version read = accepted manuscript deposited at the University of Glasgow** (*"There may be differences between this version and the published version"*).
- **A. Exact problem solved:** Resource scheduling for **RAN slicing**: how to allocate spectrum resources among multiple isolated network slices so as to **maximise resource-utilisation efficiency while guaranteeing performance isolation between slices**, under two coupled timescales — a **large timescale** (periodic traffic prediction per slice) and a **small timescale** (online reaction to inaccurate prediction and unexpected network states). Verbatim: *"due to the performance isolation, diversified service requirements and network dynamics (including user mobility and channel states, etc.), resource scheduling in RAN slicing is very challenging."* **Scheduling is the central contribution.**
- **B. Network architecture:** **5G RAN slicing / RAN sharing.** A physical RAN + CN infrastructure *"logically split into multiple virtual networks (slices) to support diverse mobile services."* The RAN comprises **N base stations (BS)** whose spectrum is **aggregated into a resource pool**; **M slices** share the RAN; slice *m* owns user subset **U_m**; **a slice may cover multiple BSs**. The design is **decentralised**: *"we transfer the control and responsibility from the mobile virtual network operator to individual slices. This stimulates the slice abilities of self-learning and self-control with reduced signaling interactions."* The paper maps its scheme onto **MORAN vs MOCN** (3GPP Rel. 15) — RAN slicing is stated to belong to the **MORAN** model (dedicated spectrum per operator) while traditional RAN resource allocation is MOCN. **No CU/DU split, no RIC, no O-RAN; no explicit SA/NSA statement.**
- **C. Network layer/domain:** **RAN** — spectrum / resource-block allocation across slices and users. Not transport, not core.
- **D. Network entities involved:** **Base Stations (N of them)** forming an aggregated spectrum resource pool; **M network slices / tenants** (each owns user subset U_m and its own TTI requirement τ_m); **users** (as members of slices); **Distributed Data Collector Units (DCUs)** — *"integrated into nearby data centers"* — that gather traffic data for the LSTM predictor; **CPU cores** hosting the parallel actor-learner agents (one per slice); a **distributed experience replay memory**; a **distributed neural network** approximating Q-value and policy; and a **shared "account book"** — *"a distributed account book to store and exchange information among slices"* used as a *"sharing account book in the Critic process, guiding the decisions to be made along the feasible way."* **No gNB, UPF, SMF, AMF, PCF, or TSN entity is named.**
- **E. Input/state parameters (exact observation vector):** The state is **not a hand-designed feature vector**; the paper defines the **"sharing (or cognitive) state space"** as the set **`{U_MI, U_MII, h_MII, r_M}`** (Section VI-A). Mapping to notation: **U_MI / U_MII** are the user sets / utilisation terms for slice classes I and II, **h_MII** is the channel state of the class-II users, and **r_M** is the allocated-resource amount for the slices. The policy network uses a **linear feature approximation** `µθ(st) = θᵀ·Φ(st)` with feature vector `Φ(st) = (φ1,….,φf)ᵀ`, **normalised** (*"the network state S as the feature vector … with f elements which need to be normalized for better performance"*). **The exact numeric feature list Φ and the value of f are NOT REPORTED in a machine-readable form in the retrieved text.**
- **F. Decision variables (exact action space):** Per-slice action **`A_m(s(t)) = a_m(t)`** — *"the fraction of resources allocated to slice m at time t"*, drawn from a **Gaussian stochastic policy** `πθ(a|s) ~ N(µ(s), σ²)`. The authors state explicitly: *"for a given slice m, the Action is defined as A_m(s(t)) = a_m(t) under the deterministic state s ∈ S, where a_m(t) is the fraction of resources allocated to slice m at time t."* Actions between slices are **unobservable to each other** — *"actions between slices are unobservable, such that each slice makes decisions independently."*
- **G. Objective function (exact cost, quoted):** This paper **minimises a cost** (note the sign convention differs from the other papers here):
  - Cost per slice: **`c_m(t) = e(r_m(t), h_m(t)) + B(D_m(t))`** (Eq. 4), where
    - **`e(r_m(t), h_m(t)) = |ln(r_m(t) − h_m(t) + 1)|`** — an elasticity/utility term, based on the logarithm function *"widely used as the elastic utility function for allocating resources"*; `r_m(t)` = resources assigned to slice m, `h_m(t)` = resources required by slice m;
    - **`B(D_m(t)) = w · 1{D_m(t) ≠ 0}`**, `w > 0` — a **bonus incurred by reconfiguration** conducted for slice m (indicator function).
  - Objective: **`Min O(πθ) = E_{ℓ∼πθ(ℓ)}[c_m(ℓ)]`** (Eq. 5) over the discounted cumulative cost `Σ γ^k r_{t+k}`.
  - Stated properties of the cost: *"(1) when r_m(t) ≥ h_m(t), with the increase of r_m(t), the cost will gradually increase towards saturation since the partial derivate ∇_{r_m} e(r_m(t), h_m(t)) gradually decreases to zero; (2) when r_m(t) ≤ h_m(t), with the decrease of r_m(t), the cost rapidly increases towards infinity, indicating the degree of resource shortage in the slice; (3) the gradient of the cost function on the left side of h_m(t) is steeper than that on the right side."*
  - When `r_m(t) < h_m(t)`, the paper transfers `r_m(t)` into `(r_m(t)/h_m(t)) + h_m(t) − 1` to keep the argument inside the log's domain.
- **H. Constraints:** (i) **Performance isolation between slices** (stated as the central design objective: *"maximize resource utilization subject to slice isolation requirements"*); (ii) **individual slice TTI requirements** — *"in order not to violate the different TTI requirements of individual slices, the DTI is set as the minimum TTI of the slices, i.e., t_Δ = arg min_{m∈M} τ_m(t)"*; (iii) **the reconfiguration-length constraint `Ω_m(D_m(t)) = 0`**, controlled through the bonus weight `w`; (iv) **a confidence-level-driven reservation constraint** — for the next prediction window the reserved spectrum is `Σ_{m∈M} r_m^U(T_Δ) = Θ_r`, where `r_m^U` is the **upper bound of the confidence interval** of the predicted traffic, chosen *"because of the penalties imposed by traffic service level agreements (SLAs)."* Constraint (2.3) is referenced as the reconfiguration constraint. **No explicit per-packet delay bound, no energy constraint.**
- **I. Scheduling algorithm + optimization method:** **iRSS** = a **collaborative DL + RL framework**:
  - **Large timescale:** **LSTM** traffic prediction per slice, over **prediction windows (PW) of 3600 s**. Confidence interval: `Pr{r_m(t) ∈ d̄ ± z_{(1−χ)/2} · σ(d)/√n} = χ` (Eq. 3), with **confidence level χ dynamically adjustable per service type**; resources reserved from the **upper bound** of the interval.
  - **Small timescale:** **Asynchronous Advantage Actor-Critic (A3C)** (Mnih et al.) solving a **continuous-time Markov Decision Process (c-MDP)** `⟨S, A, F, P, γ⟩`, with **parallel actor-learners (one per slice) and independent Actor/Critic target networks per slice**. Actor update: `∇θ O(πθ) = ∇θ log πθ(ℓ) · c(ℓ)` with **1-step update**; Critic uses **linear feature-based value approximation** `Vϑ(st) = ϑᵀ·Φ(st)` and **TD-error** `$t = V^π(st) − Vϑ(st)`, with `∇ϑ ε_πϑ = |$t|·∇ϑ Vϑ(st)`. Parameter updates `Δθ = α_{a,t}·∇θ O_m(πθ)` and `Δϑ = α_{c,t}·|w̄t|·∇ϑ Vϑ(st)`. **Parallelism is implemented by vectorising the A3C parameters** across slices.
  - **The novelty claim:** *"this is the first work to exploit DL and RL in a collaborative way for addressing RAN resource scheduling. The significance between prediction and on-line decision modules can be dynamically adjusted."*
- **J. ML/DRL used?** **YES — Deep RL: A3C (asynchronous advantage actor-critic)**, plus **LSTM** deep learning for traffic prediction. The two are coupled through an adjustable **confidence level χ**: *"if the historical traffic data collected for training the deep neural network is insufficient, the decision-making can depend more on on-line RL solution through reducing the confidence level of prediction."*
- **K. Simulator / testbed / dataset:** **Simulation only — no testbed.** Verbatim: *"We conduct this simulation in the platform of Python by using tensorflow."* **The simulator is not a named network simulator (no ns-3, no OMNeT++, no Simu5G); it is an ad-hoc Python/TensorFlow implementation.** Traffic data: *"At the beginning of the learning process of iRSS, DCU has not collected sufficient information of traffic data, and thus we use the widely used Gaussian distribution [33][34] to simulate the traffic data."* Training/validation/test split **70% / 15% / 15%**. **No dataset is named.**
- **L. Traffic model:** **Gaussian-distributed synthetic traffic** for the initial/insufficient-data phase (per the quote above), with the stated intent that real data would replace it as the DCU collects it. The LSTM is trained on this traffic with a **prediction window of 3600 s**. **No Poisson, CBR, or 3GPP TR 38.901 traffic model is used.** Channel and mobility dynamics are invoked qualitatively (*"user mobility and channel states"*) but no channel model is specified in the retrieved text.
- **M. Network scale:** **Number of slices M = 10** in the simulation (*"The number of slices M is set as 10 in the simulation experiments"*). **Number of Radio Blocks = 200.** The parameter sweep varies **network slices from 1 to 20** and **RBs from 1 to 200**. Prediction window **3600 s**; discount factor **γ = 0.99**; trace-decay **ς = 0.2**; step sizes **α_{a,t} = 10⁻⁴ (text says 10⁻⁵ in one place — see Q) and α_{c,t} = 10⁻³**. Convergence criterion: `|V_t − V_{t+1}| ≤ ε (ε = 1e−3)` within **100 policy-gradient steps**. **Number of base stations N and number of users per slice are NOT numerically reported in the retrieved text.**
- **N. Baselines:** Three, quoted: (i) **traditional (tabular) Q-learning** — *"Q-learning has poor performance in solving decision problems with continuous action space. For fair comparison, we discretize the action space first, and then choose actions by sampling"*, with *"200 decision points by using Gaussian distribution"* and learning time limited for fairness; (ii) **classic Actor-Critic (AC)** — *"the value of the mean point µ_t^Q equals to the amount of required resources in the last time, i.e., µ_t^Q = h_m(t − 1)"*; (iii) **HRSA (Heuristic Resource Scheduling Algorithm)** — *"In HRSA, each slice pre-reserves a certain amount of resources for the performance isolation. Within every DTI, HRSA configures resources to each slice from the pre-reserved resources"*, with the reservation set equal to the previous slot's requirements.
- **O. Metrics:** **Cumulated reward (cost)** over DTIs; **Resource Utilisation (RU)**, defined as `RU = Σ_t h_m(t) / Σ_t r_m(t)`; **Performance Isolation Degree (PID)** vs confidence level; **mean squared error (MSE)** of the LSTM prediction; **system average cost** vs number of slices and RBs; **convergence speed** (learning steps).
- **P. Main quantitative results (EXACT, quoted):**
  - **Resource utilisation (the headline result):** *"the RU of iRSS is higher than that of Q-learning, AC algorithms and HRSA by approximately **16.3% ∼ 19.8%**, **8.3% ∼ 13.7%**, **30.5% ∼ 34.7%**, respectively."* (Reported as ranges over the sweep of DTIs from 0 to 200.)
  - **Cumulated cost:** *"the cumulated cost of iRSS is always significantly lower than that of the AC and Q-learning algorithms."* (No numeric value given in prose — the values are in Fig. 12, a raster figure.)
  - **LSTM convergence:** *"the MSE can eventually converge to a minimum value with around **18 epochs**. Note that the dozens of epochs are much smaller than the length of PW."*
  - **A3C convergence:** *"the reward of the algorithm converges to the optimal decision rapidly with **dozens of learning steps**"*; convergence assumed when `|V_t − V_{t+1}| ≤ 1e−3` within **100 steps**.
  - **Isolation vs confidence:** *"Fig. 9 shows that the PID monotonically increases with the confidence level… if we decrease the confidence level, the isolation degree is decreased and the service requirements are violated with the probability of **1 − χ**."* Isolation degree values plotted range roughly **62% to 80%** across confidence levels **50% → 99.5%** (read off the figure axis; the prose gives no numeric PID values).
  - **Transient behaviour:** *"when the number of DTIs is smaller than **40**, the RU of Q-learning, AC, and HRSA fluctuates, while that of iRSS fluctuates mildly."*
- **Q. Constraints (Eqs. 5b–5l, quoted):** (5b) **binary RB assignment** `π^x_{m,u,f_i,t_i}[t] ∈ {0,1}`; (5c) **orthogonality** — *"each RB of RU is allocated to only one user"*; (5d)/(5e) **slice-aware RB-count constraints** `e^ur_u[t]` and `e^em_u[t]` derived from arrival rates and the uRLLC slice's dedicated RB budget `Ω`; (5f)/(5g) **per-RB power bounds** with Big-M coupling to the assignment, `0 ≤ p^em_{m,u,f_i}[t_i] ≤ π^em_{m,u,f_i,t_i}[t]·P^max_m` and `(N₀Γ₀/g_{m,u,f_i}[t_i])·π^ur_{m,u,f_i,t_i}[t] ≤ p^ur_{m,u,f_i}[t_i] ≤ π^ur_{m,u,f_i,t_i}[t]·P^max_m`; (5h) **total RU power budget** `Σ_{f_i,u,i}(p^em + p^ur) ≤ P^max_m`; (5i) **flow-split validity** `φ_u[t] ∈ φ[t]`; (5j) **rate ≥ demanded per sub-flow** `R^x_{m,u}(p^x[t_i]) ≥ φ_{m,u}[t]·λ^x_u[t]·Z^x·Δ`; (5k) **uRLLC latency bound** `τ^ur_u(π^ur[t]) ≤ D^ur`; (5l) **queue bound** `Σ_{t_i}Σ_u q_{m,u}[t_i] ≤ q^max`. **uRLLC end-to-end latency (Eq. 3)** decomposes as `τ^ur_u[t] = τ^pro_cu[t] + τ^tx_{cu,du}[t] + τ^pro_du[t] + τ^tx_{du,ru}[t] + τ^tx_{ru,u}[t] + τ^pro_ru[t]`, with the paper noting that *"thanks to the RAN slicing concept, the proposed system consistently possesses the necessary resources to instantly serve the uRLLC upon arrival"*, so **`τ^ur_u[t] ≈ τ^tx_{ru,u}[t] ≤ D^ur`**. The problem is characterised as a **mixed-integer non-linear program (MINLP)**.
- **I. Scheduling algorithm + optimization method:** A **three-step hierarchical method** — *"the proposed approach employs a three-step hierarchical process that involves **heuristics, machine learning, and convex optimization** to steer traffic flows."* Step 1 (**rAPP1, heuristic**): moving-average-based flow-split estimation `φ̂_{m,u}[t] = R̄^x_{m,u}[t] / Σ_m R̄^x_{m,u}[t]` (Eq. 6). Step 2 (**rAPP2, DDQN**): two cooperative DRL agents predict binary RB assignments `π̂[t]` per frame. Step 3 (**xApp1, near-RT RIC, CVX**): solve the convex short-term power-control subproblem `min_p Σ_{u∈U^em} q̄^em_u` s.t. (5f)–(5h),(5j),(5l) — *"Since (7) is a convex program, the standard methods can efficiently solve to obtain the optimal transmission power p*[t]."* Queue update: `q_{m,u}[t_i] = q_{m,u}[t_i − 1] + φ̂_{m,u}[t]·λ^x_u[t]·Z^x·δ_i − R^x_{m,u}[p*[t_i]]·δ_i`, rectified at 0.   `Maximize_{c_{u,t} ∈ C^NR} Σ_{t=t₀}^{∞} Σ_{u∈U} β_u · log R_{u,t}(c_{u,t}, b₁, b₂, …, b_B)`
  `subject to K_{u,t} · X_{u,t} ≤ W, X_{u,t} ∈ [0,1]`, with handover cost **`K_{u,t} = K₀·e^{−δ·(t−t⁰_u)}`** and **X_{u,t}** a 0/1 handover indicator. **After Lagrangian relaxation (Eq. 2):** `Maximize Σ_t Σ_u β_u·log R_u(c_{u,t}, b₁,…,b_B) − K'·e^{−δ(t−t⁰_u)}·X_{u,t} + W'`, with `K' = λK₀`, `W' = λW`, `λ ≥ 0`.
  **RL reward (Eq. 3):** **`R_{u,t+1} = β_u · (log R_{u,t+1}(c_{u,t+1}) − log R_{u,t}(c_{u,t})) − k(c_{u,t+1})`** — *"The reward for UE u is the improvement in the logarithmic throughput R_{u,t} due to the transition from ~s_{u,t} to ~s_{u,t+1} caused by action a_{u,t} taken at t, **minus the cost factor**. The reward is positive, if the improvement in log throughput is higher than the cost, and negative, otherwise."* **Value function:** `V^π(s) = E[Σ_{u∈U} Σ_{i=0}^{∞} γ^i R_{u,t+i} | ~s_{u,t} = s, π(a|s)]` (Eq. 4).
- **H. Constraints:** (i) **Handover cost threshold** `K_{u,t}·X_{u,t} ≤ W` — *"We add this cost function as a constraint to make sure that the cost does not exceed a predefined cost threshold"* (W = *"a predefined cost threshold, which represents a maximum value that cannot be exceeded by the cost function"*); (ii) `X_{u,t} ∈ [0,1]`; (iii) `λ ≥ 0`. **The objective itself encodes the *infinite-horizon* discounted log-throughput maximisation.** No explicit per-flow delay or QoS constraint is imposed.
- **I. Scheduling algorithm + optimization method:** **REM (Random Ensemble Mixture) — a Conservative Q-Learning (CQL) algorithm — combined with a state-of-the-art Convolutional Neural Network (CNN) architecture**, trained **offline** (offline RL, following Levine et al. and Kumar et al.'s CQL). The paper claims: *"To the best of our knowledge, this is the first paper to develop a data-driven UE-based traffic steering/handover optimization technique based on Conservative Q-learning."* CQL is used because *"testing poorly trained solutions or performing [online exploration]…"* in production is unsafe; REM *"enforces optimal [behaviour]… minimize REM Q-value under π."* **CNN architecture (Fig. 4 / Table 1):** **Conv1D layer** with **filters = 32, kernel size = 8, strides = 8, activation = ReLU**; **Flatten layer** (225 neurons); **Dense Layer 1 = 128 neurons**; **Dense Layer 2 = 32 neurons**; **Dense Layer 3 = 1400 neurons**; **Number of heads (n_heads) = 200**; **Number of actions (N) = 7**.
- **J. ML/DRL used?** **YES — Deep RL, offline/Conservative RL: CQL with Random Ensemble Mixture (REM)**, on a CNN function approximator. **Plus supervised-learning-free offline data collection** via ns-O-RAN.
- **K. Simulator / testbed / dataset:** **ns-3 (discrete-event network simulator) + a real, production-grade near-RT RIC** — this is the paper's central artifact, **ns-O-RAN**: *"a software framework that integrates a real-world, production-grade near-RT RIC with a 3GPP-based simulated environment on ns-3."* Components: **ns-3 with the 5G mmWave/LENA module** (3GPP-compliant channel/PHY); **e2sim** extended to support multiple endpoints with independent C++ objects and per-endpoint socket addresses; **message dispatching** with unique ports per simulated base station; **time synchronization** between wall-clock (Unix ms baseline) and ns-3 simulation time. **This is a hybrid: a real RIC control plane in the loop with a simulated RAN — NOT a real over-the-air testbed, and NOT a pure simulator.** **Dataset:** *"The data collection is based on a total of more than **2000 simulations** for the different configurations, including multiple independent simulation runs for each scenario"*; the agent was trained **offline** on *"more than **40 million data points** collected by ns-O-RAN."* **Code:** ns-O-RAN is released **open-source in the O-RAN Software Community** (`github.com/o-ran-sc/sim-e2-interface` is referenced for e2sim).
- **L. Traffic model:** *"The users request downlink traffic from a remote server with a **mixture of four traffic models, each assigned to 25% of the UEs**"*: (i) **full buffer Maximum Bit Rate (MBR)** traffic saturating at **R_fb,max = 20 Mbit/s** (*"to simulate file transfer or synchronization with cloud services"*); (ii) **bursty traffic with average data rate R_b,max = 3 Mbit/s** (*"to model video streaming applications"*); (iii) **two bursty traffic models with average data rates of 750 Kbit/s and 150 Kbit/s** (*"for web browsing, instant messaging applications, and Guaranteed Bit Rate (GBR) traffic (e.g., phone calls)"*). *"The bursty traffic models feature on and off phases with a random exponential duration."* **Channel model: 3GPP UMa (Urban Macro) street canyon** per **3GPP TS 38.901**. **Mobility: Random Walk** with *"minimum speed S_min = 2.0 m/s and maximum speed S_max = 4.0 m/s"* (*"pedestrian to slow vehicle mobility"*).
- **M. Network scale:** **Up to 126 users (N_UE) with 8 NR gNBs** — the headline configuration. User counts swept: **42, 63, 84, 105, 126**. - **N. Baselines:** Four, quoted: (i) **RAN RRM heuristic** — *"decides to perform a handover if a target cell has a channel quality metric (in this case, the SINR) above a threshold (specifically, **3 dB**) with respect to the current cell"*; (ii) **SON1** — *"assumes a **fixed TTT**, i.e., the handover is triggered only if the target cell SINR is above a threshold (3 dB) for a fixed amount of time (**110 ms**)"*; (iii) **SON2** — *"uses a **dynamic TTT**, which is decreased proportionally to the difference between the target and current cell SINR"*; (iv) an implementation of the **contextual multi-armed bandit (CMAB) RL agent from Yajnanarayana, Rydén & Hévizi (IEEE 5GWF 2020)** — *"we implemented the agent from [29] in the xApp, and trained it on the same dataset used to train our agent."* Also a **handovers-disabled** reference configuration.

- **Q. Main limitation:** **Author-acknowledged:** (i) the agent **triggers more handovers at 42 UEs** (low load), attributed to the reward's logarithmic throughput gain outweighing the handover cost; (ii) **the proposed agent does not improve cell-edge (10th-percentile) throughput relative to the CMAB baseline from [29]** — *"However, this does not improve the cell-edge throughput"*. **Methodological:** (a) **The RAN is simulated in ns-3, not a real radio** — the near-RT RIC is real, but the E2 nodes, UEs, and channel are simulated, so results do not capture real propagation, hardware scheduler behaviour, or real UE implementation; (b) **the evaluation is a single scenario family** (8 gNBs, fixed ISD, two bands, random-walk mobility at pedestrian speeds 2–4 m/s) — no high-speed, no dense-urban, no interference-limited sweep; (c) the **action space is one handover target per UE with the same agent controlling all UEs**, so inter-UE coordination is only implicit; (d) **offline CQL training on >40M points requires 2000+ simulations**, so the data cost of the approach is substantial and not analysed as a limitation; (e) **no energy, no URLLC/latency metric, no QoS-flow or slice-level metric** — this is a pure throughput/mobility-overhead optimisation; (f) the **the paper's own framing (*"the first user-specific O-RAN TS intelligent handover framework"*) means it predates competing O-RAN TS work**, so no comparison against the DDQN/FML TS papers in §8 exists; (g) **the retrieved version is a preprint**, so numbers should be re-verified against the TMC version of record before citation.
- **R. Research gap this suggests:** (i) **The simulation-to-real gap**: ns-O-RAN puts a real RIC in the loop but a simulated RAN — validating the same xApp on **real O-RAN hardware / OTA testbeds (e.g. Colosseum, Arena, OpenAirInterface)** is the obvious next step, and ns-O-RAN itself is the tool that makes it feasible; (ii) **the cell-edge / 10th-percentile weakness** is an explicit, quantified shortfall — a **fairness-aware or percentile-constrained** traffic-steering reward is a concrete contribution; (iii) **the low-load handover-chatter problem at 42 UEs** means the handover-cost model is mis-calibrated at low load — an **adaptive cost function** is open; (iv) **latency/URLLC and energy are entirely absent** from the objective — extending O-RAN TS to multi-KPI (throughput + latency percentile + energy) optimisation is open; (v) **the action space is handover-only** — the paper does not jointly optimise **cell selection + carrier/BWP assignment + slice/QoS-flow steering**, so the *"traffic steering"* in O-RAN terminology (which nominally spans RAT selection, carrier aggregation, and QoS-flow-to-bearer mapping) is only partially addressed; (vi) **the offline-CQL data requirement (>40M points, 2000+ simulations)** makes the approach expensive to re-train for new deployments — sample-efficient or transfer-learning variants are open; (vii) **no head-to-head comparison with the other O-RAN TS RL approaches** (DDQN at non-RT RIC in §8a; federated meta-learning in §8b; contextual bandits) on a common benchmark — a unified O-RAN TS benchmark suite is a clear community gap.

### 11. LEARNET: Reinforcement Learning Based Flow Scheduling for Asynchronous Deterministic Networks

- **Authors / Year / Venue / DOI / peer-reviewed or preprint:** Jonathan Prados-Garzon, Tarik Taleb, Miloud Bagaa. **2020** (published 01/06/2020). *ICC 2020 — 2020 IEEE International Conference on Communications (ICC)*, Dublin, Ireland, **pp. 1–6**. **DOI: 10.1109/ICC40277.2020.9149092**. **Peer-reviewed conference paper.** Affiliations: Aalto University, Espoo, Finland; University of Oulu, Finland. - **A. Exact problem solved:** The **Online Flow Allocation Problem (OFAP) in DetNet asynchronous networks**. Verbatim: *"The OFAP in an ATS-based FP considered here is defined as the process of choosing the allocation configuration for every incoming flow at every hop all along the predefined path from its source to its destination in order to maximize the network operator's revenue. The flow allocation configuration at every ATS implies to decide the flow to **shaping buffer, priority level, and delay budget assignments**."* Stated novelty: *"To the best of the authors' knowledge, this is the **first paper proposing a RL-based solution for optimizing the operation of a TSN asynchronous forwarding plane**."* Prior art: only Specht & Samii [8], who used an **SMT solver** and a heuristic **Topology Rank Solver (TRS)** maximising delay slack. **Scheduling is the central contribution.**
- **B. Network architecture:** **SDN-like DetNet architecture with fully separated Control Plane (CP) and Forwarding Plane (FP).** FP = **V IEEE 802.1 TSN devices**, each with an **IEEE 802.1Qcr Asynchronous Traffic Shaper (ATS)** at every egress port; modelled as a directed graph **G = (V, E)**, E/2 full-duplex point-to-point links. Two node types: **DEN (DetNet Edge Node)** — adds/removes packet sequencing and does replication/combination; **DTN (DetNet Transit Node)** — DetNet forwarding sub-layer only. CP = logically centralised **SDN controller** with three applications: **ME (Monitoring Engine)**, **DAE (Data Analytics Engine)**, **FSA (Flow Scheduling Application — where LEARNET lives)**. **ATS internals (2-level queueing):** level 1 = **shaped queues** for interleaved shaping; level 2 = **one pseudo-queue per priority level**, all **FCFS**. **Shaping algorithm = Length Rate Quotient (LRQ)**, enforcing `A_f(t) ≤ r_f·t + b_f`. **QAR rules (QAR1–QAR3):** *"each shaped queue is associated with only one ingress port (QAR1), one priority level in the previous ATS (QAR2), and one internal priority level (QAR3) at a given time."* **Routing is GIVEN:** *"explicit routes between every pair of DENs source and destination in the network is predefined."*
- **C. Network layer/domain:** **IEEE 802.1Qcr ATS forwarding plane (Layer 2)** inside an **IETF DetNet** network; evaluated as a **5G DetNet Backhaul Network (BN)** — i.e. **transport/backhaul domain**, per-flow **per-hop** granularity. Control plane operates as SDN applications. **Not RAN, not 5G Core.**
- **D. Network entities involved:** **DEN**, **DTN**, **ATS** (one per egress port), **shaped queues / shaping buffers** (size B_s, idle/busy state), **pseudo-queues**, **SDN controller**, **ME / DAE / FSA**, the **RL flow-scheduling agent**, a **Flow Admission Control** block, a **Flow Information Base**, and the **foi (flow of interest)**. **No gNB, UPF, or 5G core NF appears** — this is a wired deterministic-transport paper.
- **E. Input/state parameters (exact, quoted):** **Flow request parsing:** *"LEARNET needs to know the **sustainable rate r^(foi)**, **burstiness b^(foi)**, **maximum packet size l^(foi)**, and **E2E delay budget of the foi**."* **Predictive analytics:** *"i) the expected foi **lifetime duration τ^(foi)**, ii) the foreseen **arrival rate λ** during the next temporal interval of length τ^(foi), and iii) the predicted **mean and standard deviation for the different features of the future incoming flows** (r, σ_r, b, σ_b, D_max, and σ_Dmax)."* **Network information:** *"i) **link capacities C_{e_l}** ∀ e_l ∈ P; ii) **current state of the shaping buffers** at the different ATSs P in the foi path; and iii) the **allocated rate r_p^(e_l)**, **allocated burstiness b_p^(e_l)**, **minimum delay budget D_{p,max}^(e_l)**, and **maximum packet length l_p^(e_l)** at each priority level of every ATS in the foi path."* Modelling assumptions stated: *"i) the flow lifetime duration obeys an **exponential distribution**, ii) the flow arrival process is **Poissonian**, and iii) the flow arrival process and the features of the future incoming flows to the system are **stationary**."*
- **F. Decision variables (exact action space, quoted):** *"Let us suppose the predefined path for the foi has **N_H hops**. Then, the action generated by the agent is an **N_H dimensional vector of real numbers u**, where each component includes two data: i) the chosen **priority level p_a^(e_l)** for the foi at the respective hop (ATS) e_l, ii) the **percentage of the total foi E2E delay budget η^(e_l) = D_{p,max}^(e_l)/D_max^(foi)** to be spent at the respective hop… The former is included in the **integer part** of the component, whereas the latter is contained in the **decimal part**."* Range: each component ∈ [1, P_max^(e_l) + 1]; decimal part discretised (e.g. granularity 0.1 = 10% steps). **Action filtering:** *"c.1) the sum of the decimal parts of all components of u has to equal one, and c.2) the decimal part of every component of u has to be greater than zero."* Worked example: for 3 hops and P_max = 3, `u = (1.5, 3.5, 1.0)` and `u = (1.2, 3.5, 1.2)` are removed; `u = (2.2, 3.5, 1.3)` is valid. **The shaping buffer is then chosen by the admission-control algorithm, not the RL agent.**
- **G. Objective function (exact reward, quoted):** *"If the flow is **accepted**, the agent will receive an award **1/τ^(foi) times the income α^(foi)** that the operator will obtain for allocating the foi. If the flow is **rejected**, the agent will be penalized with a reward of **−1/τ^(foi) · α^(foi)**."* → **`R = ±α^(foi) / τ^(foi)`**. *"Observe that, if we set **α^(foi) = 1 for all the incoming flows**, we will maximize the **flow acceptance ratio** (flow rejection ratio minimization)."* Global objective: *"maximize the network operator's revenue."* Income parameterisation: income *"might be different for each flow depending on the type of flow or the flow characteristics, e.g., mean sustainable rate r_f, burstiness b_f, maximum packet length l_f, and maximum end-to-end (E2E) delay budget D_{f,max}."*
- **H. Constraints (C1–C5, verbatim):** **C1** *"The E2E delay D experienced by the foi has to be lower than its E2E delay budget D_{f,max}"*; **C2** *"The ongoing flows must keep experiencing an E2E delay lower than their respective E2E delay budgets"*; **C3** *"The aggregated rate allocated to any link must be lower than its capacity"*; **C4** *"The aggregated burstiness allocated to any shaping buffer has to be lower than its size"*; **C5** *"The QAR1, QAR2, and QAR3 rules have to be met."* Plus action-space constraints c.1/c.2 (above). **Analytical delay bound (Eq. 1):** `D_{f,p}^(e_l) ≤ [Σ_{z=1}^{p} b_z + max_{z=p+1..P_max}(l_z)] / [C_{e_l} − Σ_{z=1}^{p−1} r_z] + l_f/C_{e_l}`. **Link capacity check (Eq. 5):** `Σ_{z=1}^{P_max} r_z^(e_l) + r^(foi) ≤ C_{e_l}, ∀ e_l ∈ P`. **Algorithm 1** ("Shaping buffers related constraints verification and allocation process for the foi") searches for a **busy** buffer matching input port + internal priority level + previous-hop priority level with `B_s ≥ b^(foi)` → ACCEPTED/ChooseBusyBuffer; else any **idle** buffer → ACCEPTED/ChooseIdleBuffer; else **REJECTED**. Constraints:** (i) **Latency constraint (soft, penalised)** — `l_h ≤ l_r`, with `l_r` derived from the session's 5QI; **not structurally enforced**: *"Note that our approach **cannot guarantee any level of latency error rate**, even though a different trade-off with energy efficiency can be achieved by tuning the reward function"*; (ii) **Host capacity constraint** — masked out of the action space by Maskable PPO (*"hosts that are full and not capable of accepting any other PDU sessions"*); (iii) **Bandwidth/throughput** — each edge host has a *"maximum available bandwidth"*, each session a *"required bandwidth"* and *"desired throughput"*; (iv) **Cloud treated as unconstrained** (explicit modelling assumption); (v) the paper notes the underlying problem is **NP-hard** (*"The problem of finding the optimal distribution of VNFs in a data center network to minimize energy consumption has been shown to be NP-hard"*), hence RL rather than constrained optimisation. **No explicit per-flow delay bound, no SLA formulation, no energy budget.**
- **I. Scheduling algorithm + optimization method:** **Maskable Proximal Policy Optimization (Maskable PPO)**, trained for **6M steps with 1000 steps per episode**, implemented with **Stable-Baselines3**; the agent selects a host **per incoming PDU session request**. **Two copies of the same PPO algorithm** are trained and compared: one observing/optimising **power consumption**, the other substituting **CPU utilisation** in both observations and reward (an ablation).
- **J. ML/DRL used?** **YES — Deep RL: Proximal Policy Optimization (PPO), Maskable variant**, from Stable-Baselines3. The paper frames the problem as an MDP and notes *"Model-free DRL algorithms, such as Deep Q-Networks and PPO, do not require knowledge of the transition probability matrix."*
- **K. Simulator / testbed / dataset:** **Simulated environment for both training and testing, with power/CPU models empirically derived from a real hardware testbed.** Verbatim: *"we decided to implement a simulated environment using the framework provided by the **Gymnasium** library and the **Stable-Baselines3** algorithms."* / *"both training and testing environments are **simulated** using power consumption and CPU models **empirically derived from a real-world small-scale testbed** described in our previous study [1]. Each experimental model describes the power consumption and CPU usage of a specific host based on the traffic load as a percentage of the maximum throughput… The power consumption is measured with a **smartplug** connected to the hardware hosting the 5GC, therefore it shows the aggregate power consumption of the system."* Reference [1] = Bellin, Granelli, Munaretto, *"A measurement-based approach to analyze the power consumption of the softwarized 5G core,"* **Computer Networks, vol. 244, p. 110312, 2024.** **Table I experimental power models (verbatim, traffic load 0%→100% in 10% steps):** **Virtual machine** — Power [W] 9.47, 10.67, 12.44, 14.77, 17.88, 20.99, 24.05, 27.03, 28.72, 29.83, 30.47; CPU [%] 5.3, 27.2, 38.8, 42.4, 43.2, 52.3, 62.4, 67.0, 70.9, 74.3, 77.2. **Bare metal** — Power [W] 8.20, 8.94, 9.71, 10.49, 11.47, 13.08, 14.18, 15.24, 16.18, 16.92, 17.33; CPU [%] 0, 8.5, 11.5, 12.3, 12.4, 13.1, 12.2, 14.4, 16.1, 16.6, 17.7. **Containers** — Power [W] 7.90, 9.62, 10.92, 12.40, 14.21, 16.06, 17.83, 19.10, 20.08, 20.88, 21.55; CPU [%] 1.0, 10.5, 13.4, 14.3, 14.9, 14.0, 16.7, 18.2, 20.7, 24.1, 26.1. **No live 5GC testbed was used for the DRL evaluation** — *"For the scope of this study, both training and testing environments are simulated."* **No named public dataset.**

- **M. - **N. - **P. Main quantitative results (EXACT, quoted):**

- **Q. Main limitation:** **Fully simulated evaluation** (*"For the scope of this study, both training and testing environments are simulated"*), with the real testbed contributing only **empirical power/CPU models from identical hardware** — the authors identify this themselves as the reason the power-vs-CPU comparison shows no benefit. The approach **cannot guarantee any latency-error level**. Retraining is required for environmental change: *"bigger environment changes, such as the addition of a new edge host or a complete change in traffic characteristics, will require the retraining of the DRL model."* The **cloud is assumed infinitely scalable with no bandwidth cap**, removing a key constraint. **Only three 5QI values are used and priority levels are not exploited** (*"We also want to evaluate the algorithm using more 5QI values and include their priority level in the reward function"* — future work). **Only 4 hosts and 1000 requests** in the main scenario; **no UE/PDU-session/geographic scale is reported.** **No real 5GC deployment**: the authors' next step is *"testing the orchestrator in a real-world deployment with a more complex architecture and a wider selection of hardware."*
- **R. Research gap this suggests:** (i) **Real-deployment validation is missing** — a live 5GC (Open5GS / free5GC + real UPFs) on **heterogeneous** hosts is the explicit next step and a strong PhD contribution; (ii) **heterogeneous hardware and renewable-energy awareness** — *"It allows the integration and modeling of renewable energy sources. This aspect is not explored in our work"* — **carbon-aware UPF selection** is an explicit open problem; (iii) **only 5QI → latency mapping is used; 5QI priority, GBR/non-GBR, and QoS-flow-level (not just PDU-session-level) granularity are unexploited** — **QoS-flow-level scheduling inside/between UPFs is not addressed by this paper or any paper found in this search**; (iv) **no guarantee mechanism** — the latency constraint is only softly penalised, so a **safe / constrained-RL formulation with hard SLA guarantees** is open; (v) **no coupling with the RAN slice scheduler** — end-to-end (RAN + core) slice/QoS orchestration remains unaddressed across the whole set of papers in this review; (vi) **no PDU-session-duration observability** — the agent is disadvantaged by not knowing session duration, which a predictive/forecasting extension could fix.
